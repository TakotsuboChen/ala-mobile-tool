## 2. 本次会话重大突破 — perfetto trace 定位到根因

### 根因：`getAllUncoveredSemanticsNodesToIntObjectMap` 每次 17ms（KSU 1.5ms）

用 `adb shell perfetto -d -a tools.alamobile.mod -o ... -t 8s sched gfx view input wm` 抓到了 release 构建的 Compose trace。

**交互时精确对比（同设备、同依赖、同代码结构）：**

| 指标 | 我们 | KernelSU | 倍数 |
|---|---|---|---|
| getAllUncoveredSemanticsNodes avg | 7.4ms | 0.5ms | **15x** |
| getAllUncoveredSemanticsNodes max | 17ms | 1.4ms | **12x** |
| Recomposer:animation avg | 9.7ms | 0.7ms | **14x** |
| Recomposer:animation max | 29ms | 3.8ms | **8x** |
| checkForSemanticsChanges avg | 15.8ms | 0.8ms | **20x** |
| Recomposer:recompose avg | 0.5ms | 0.1ms | 5x |

**animation phase 内部对比（单帧）：**
- 我们: `getAllUncoveredSemanticsNodes` 12.9-16ms + `AndroidOwner:measureAndLayout` 4-6ms + `Recomposer:recompose` 0.8-5.7ms + `semantics:boundUpdates` 1.2ms = ~25ms 子 slice
- KSU: 只有 `VectorDrawable repaint` x7-8（每次 0.2-3ms）= ~5ms 子 slice。**没有 Compose recompose/semantics 开销**

**draw phase 对比（不是问题）：**
- 我们 draw-VRI avg=2.2ms，KSU avg=2.8ms——我们的 draw 甚至更快
- 问题完全在 animation phase 的 Compose composition/semantics

### 为什么 KSU 的 animation phase 没有 Compose recompose？

KSU 每帧都调用 `Recomposer:animation`（707次/6秒 ≈ 118fps），但每次 avg=0.7ms。
这说明 KSU 的 composition 树已稳定——recompose 只是空跑检查（没有实际变化）。

我们只在有变化时调用（161次/8秒 ≈ 20fps），每次 avg=9.7ms。
每次变化触发的 recompose 范围很大——需要重新计算整个 semantics 树。

### 最小复现确认：miuix SwitchPreference 是性能瓶颈

**关键实验**：把 ConfigActivity 简化到最小——不用 NavDisplay、HorizontalPager、ViewModel、LSPosed binding。

| 配置 | Janky% | P50 | Frames |
|---|---|---|---|
| 纯 Compose Text（无 miuix，release） | **2.80%** | 7ms | 1428 |
| 纯 Compose Text（无 miuix，debug） | 16.39% | 9ms | 909 |
| miuix SwitchPreference ×30（release） | 22.33% | 13ms | 645 |
| 禁用 LSPosed binding + miuix SwitchPreference | 22.33% | 13ms | 645 |
| 完整 3 page（切 tab，release） | 42% | 20ms | 1032 |
| KSU 垂直滑动（同条件） | **0.10%** | 9ms | 1950 |

**根因定位**：
- 纯 Compose Text 只 2.80% → **排除 Compose 运行时/LSPosed 环境**
- 加 miuix SwitchPreference 跳到 22.33% → **miuix SwitchPreference 是主要开销源**
- 但 KSU 用同样的 miuix 0.9.3 + SwitchPreference 只 0.10% → **差异不在 miuix 版本**

## 5. 下一步（有序）

### 核心谜题

两个 app 用**完全相同的依赖、相同的代码结构、相同的设备**，但 semantics 树遍历速度差 15 倍。

KSU 每帧都跑 recompose 但空跑（0.7ms），我们只在变化时跑但每次重算（9.7ms）。
KSU 的 animation phase 只有 VectorDrawable repaint，我们有 Compose recompose/semantics。

### 调查方向

1. **用 Compose Layout Inspector 对比 semantics 树节点数** — 在 Android Studio 中打开 Layout Inspector，选择 semantics 树视图，对比两个 app 的节点总数和深度。这是最直接的验证方法

2. **检查是否有 LSPosed 注入的代码干扰 Compose** — 我们是 LSPosed 模块，App.onCreate 里做了 XposedServiceHelper.registerListener + NPatch ContentProvider.call。这些可能在 ConfigActivity 运行时产生主线程 Binder 调用。检查 perfetto trace 中是否有 ConfigActivity 主线程的 binder transaction

3. **对比两个 app 的 APK 中 R8 处理后的 Compose 类** — 用 `dexdump` 检查两个 APK 的 classes.dex，确认 Compose 相关类是否被 R8 以相同方式优化

4. **用最小复现项目验证** — 创建一个全新的空 Android 项目，只引入 miuix + Compose BOM，不做任何 LSPosed/Xposed 相关配置。如果它也卡 → 问题在 miuix/Compose；如果它不卡 → 问题在 LSPosed 模块环境

5. **检查 LSPosed/Xposed 框架是否注入了 View 处理** — LSPosed 可能在 ConfigActivity 的 ViewRootImpl 上注入了 hook，导致每帧额外的 semantics 处理。检查 LSPosed 日志和 hook 列表

## 6. perfetto trace 命令（已验证可用）

```bash
# 抓我们的 trace
adb shell perfetto -d -a tools.alamobile.mod \
  -o /data/misc/perfetto-traces/ala.pb -t 8s \
  sched gfx view input wm

# 抓 KSU trace
adb shell perfetto -d -a me.weishu.kernelsu \
  -o /data/misc/perfetto-traces/ksu.pb -t 8s \
  sched gfx view input wm

# 拉取
adb pull /data/misc/perfetto-traces/ala.pb /tmp/ala.pb

# 解析（需要 pip install --break-system-packages perfetto）
python3 -c "
from perfetto.trace_processor import TraceProcessor
tp = TraceProcessor('/tmp/ala.pb')
result = tp.query('''
SELECT s.name, s.dur, COUNT(*) as count
FROM slice s
WHERE s.name LIKE '%Compose%' OR s.name LIKE '%semantics%' OR s.name LIKE '%Recomposer%'
GROUP BY s.name
ORDER BY MAX(s.dur) DESC
LIMIT 20
''')
for row in result:
    print(f'{row.dur/1000000:.1f}ms  x{row.count}  {row.name}')
"
```

## 7. gfxinfo framestats 命令（已验证可用）

```bash
# 重置
adb shell dumpsys gfxinfo tools.alamobile.mod reset

# 抓 framestats
adb shell dumpsys gfxinfo tools.alamobile.mod framestats > /tmp/fs.txt

# 解析 phase breakdown（25 列 CSV）
awk -F, '/^0,/ && NF>=25 && $6+0 > 0 {
  handleInput=$6; anim=$7; traversals=$8; drawStart=$9; syncQ=$14; syncStart=$15; issueDraw=$16; swapBuffers=$17; frameCompleted=$18;
  total = (frameCompleted - handleInput) / 1000000;
  if (total > 8.3) {
    input_dur = (anim - handleInput) / 1000000;
    anim_dur = (traversals - anim) / 1000000;
    traversal_dur = (drawStart - traversals) / 1000000;
    draw_dur = (syncQ - drawStart) / 1000000;
    sync_dur = (syncStart - syncQ) / 1000000;
    issue_dur = (swapBuffers - issueDraw) / 1000000;
    printf "total=%.1fms input=%.1f anim=%.1f traversals=%.1f draw=%.1f sync=%.1f issue=%.1f\n", total, input_dur, anim_dur, traversal_dur, draw_dur, sync_dur, issue_dur
  }
}' /tmp/fs.txt | head -15
```
