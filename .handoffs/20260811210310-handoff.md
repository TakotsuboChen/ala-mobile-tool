## 3. 决策与理由
- **激活判定改双路径** [V]——`hasModuleLoadedFlag()`（目标进程路径：`onModuleLoaded` 执行过 = 被真正注入）优先；其次 `service != null && getScope().isNotEmpty()`（ConfigActivity 进程路径）。否决"只用 onModuleLoaded property"：`onModuleLoaded` 只在目标进程（游戏）调，ConfigActivity 进程**从不调**，property 永远 false → 永远显示未激活（用户实测"获取不到激活状态"）。
- **`getScope()` 仍有残留误判** [V]——scope 存在 LSPosed daemon SQLite DB，独立于模块启用/禁用状态，`pm clear` 清不掉。所以"清数据 + 关开关 + 第一次打开"仍可能误判已激活；第二次打开（进程重启，daemon 不再推 binder，service=null）才走 Non-root 路径。这是 ConfigActivity 进程信号可达性的现实折中。
- **`markActivated()` 保留 setProperty，但文档纠正** [V]——property 对目标进程可靠，对 ConfigActivity 不可达，是双路径之一，不再自称"唯一/核心"。
