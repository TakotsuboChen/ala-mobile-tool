# docs 文档规范与索引

> 状态：**活跃** · 最后编纂：2026-10-26
> 一句话结论：所有研究结论必须落盘，按「研究 → 发现 → 固化」三段式写，**永不删除已否决的方案**。

---

## 0. 为什么有这份规范

这个项目的知识几乎全部来自逆向工程与实机验证，成本极高：

- 一个字段偏移要反汇编几十条指令才能确认
- 一个 hook 点选错要装机跑圈才能暴露
- 一条「这条路不通」的结论背后往往是数小时的试错

**这些结论一旦丢掉，下次会话就要从头再挖一遍。** 本项目已经发生过多次：
同一个坑被反复踩（`carModifier.cM` 探针、日志截断掩盖证据、NPatch 缓存问题三次复发）。

所以本规范的核心不是「文档要好看」，而是：

1. **写下来** —— 研究做完当场写，不留到下次会话
2. **写对地方** —— 原理归原理、实现归实现，不要混在一篇里
3. **写清楚可信度** —— `[V]` 验证过 / `[?]` 待验证 / `[X]` 已证伪
4. **永不删除** —— 已否决的方案是资产，删掉就会有人再试一次

---

## 1. 文档骨架（强制）

**每篇文档从头就按这个结构写**，不要先随便写再改：

```markdown
# <主题>

> 状态：活跃 / 冻结 / 已归档 · 最后编纂：YYYY-MM-DD
> 一句话结论：<给赶时间的人看的一句话>

## 1. 结论（发现）
可直接采信的事实。每条带证据等级 [V] / [?] / [X]。

## 2. 依据（研究）
怎么查出来的：反汇编地址、实机日志片段、源码对照、资源解析。
**保留原始证据**（指令、日志行、字节），不要只写"经分析确认"。

## 3. 实现（固化）
模块里对应哪段代码、哪个偏移常量、哪个配置开关、哪个日志特征串。
让下一个人能直接定位到代码。

## 4. 已否决的方案
试过但失败的方案 + 失败原因 + 失败时的现象指纹。
**永不删除**——这是最容易重复踩的坑。

## 5. 待验证
[?] 项清单，每条写清「依赖什么才能验证」。
```

### 可选节（按需增删）

- `## 6. 升级检查清单` —— 游戏版本升级时必须重新核对的事项
- `## 附录` —— 大表格、完整数据转储

## 2. 分流规则：新发现该写哪

| 内容类型 | 去处 | 判据 |
|---|---|---|
| **引擎机制、逆向结论** | `TECHNICAL_ANALYSIS.md` | 讲的是"游戏怎么运作"，与模块无关也成立 |
| **模块实现、踩坑记录** | `notes/<主题>.md` | 讲的是"模块怎么做"，换实现就失效 |
| **设计决策、跨仓契约** | `design/<主题>.md` | 讲的是"为什么这么定"，约束后续改动 |
| **已失效、仅存历史** | `archive/` | 内容已被取代，但删除会丢教训 |

### 边界判定口诀

> 问自己：**"如果模块重写一遍，这条还成立吗？"**
> - 成立 → 原理类，进 `TECHNICAL_ANALYSIS.md`
> - 不成立 → 工程类，进 `notes/`

### 跨仓契约

`design/PADDOCK_PLAN.md` 是模块与 `ala-mobile-paddock` 服务端的**唯一契约源**。
任何 API 形状、积分公式、字段语义变更，必须在同一会话内同时改两侧代码与本文件。

## 3. 编纂规则（勤于编纂）

### 3.1 什么时候写

- **当天**：任何经过验证的发现，当天写进对应文档
- **不许攒**：不要想着"等这波做完一起写"——会话结束就忘了
- **失败也写**：试过不通的方案立刻进 §4，不要等确认"真的不通"

### 3.2 ⚠️ 历史遗留问题：`/handoff` 不是知识沉淀

**这是本规范要解决的核心问题，先看清成因。**

`/handoff` 的设计目标是「**给下一个会话看的状态快照**」，不是「知识沉淀」。所以它记的是：

- "这次做到哪了" → 状态，下一次会话就过期
- 而不是 "我们学到了什么" → 知识，应该长期有效

结果是：**187 份 handoff 归档、约 2400 条 `[V]` 结论，全部埋在 `.handoffs/` 里，没有索引、没人会翻，等于丢了。**

抽样实证（这些结论都有价值、都没进 `docs/`）：

| handoff | 只存在于归档的研究结论 |
|---|---|
| `20260906170000` | `{{at_me}}` @车手五轮实测矩阵定案、金标播报紧凑版分层、迪拜赛道正名三处联动 |
| `20261003222408` | 金标播报迁移幂等验证、真库测试 9 passed、部署链四轮流程 |

**CLAUDE.md / memory 只兜住了"高频引用"的结论**（反复踩的坑），
**一次性的、低频但仍有价值的发现没有任何落点**——这是结构性缺口，不是疏忽。

### 3.3 回收已丢失的研究成果

`.handoffs/` 里的内容按以下判据分流：

| handoff 内容 | 处理 |
|---|---|
| 具体研究结论（字段含义、hook 选型、实测矩阵、踩坑） | **回收**进对应 `docs/` 文档 |
| 纯状态（"工作区 clean"、"已推送"、构建耗时） | 丢弃，无长期价值 |
| 已被后续推翻的结论 | 回收进对应文档 §4「已否决的方案」，标 `[X]` |
| 项目约定 / 红线 | 进 `CLAUDE.md` 或 memory |

**回收不是抄一遍**：要按五节骨架重新组织，同一主题的多条结论合并成一条，
补上现在的状态（是否仍然有效）。

**回收进度**记录在本文件 §7。

### 3.4 什么时候编纂旧内容

每次修改一篇文档时，顺手做一次编纂：

1. **过时结论** → 标 `[X]` 并说明被什么取代，移到 §4
2. **已实现的设计** → 从"待验证"移到"结论"
3. **重复内容** → 合并，保留更完整的那份
4. **过程叙述** → 压缩成结论 + 证据，删掉"我先试了…然后发现…"的流水账
5. **文档头** → 更新「最后编纂」日期

### 3.5 状态标记

| 状态 | 含义 | 行为 |
|---|---|---|
| **活跃** | 当前有效，持续维护 | 正常读写 |
| **冻结** | 结论稳定，不再补充 | 只在发现错误时改 |
| **已归档** | 已被取代 | 只读，不再修改 |

## 4. 证据等级

| 标记 | 含义 | 例子 |
|---|---|---|
| `[V]` | 已验证 | 实机日志确认 / 反汇编实证 / 命令输出 |
| `[?]` | 待验证 | 推断、记忆、未经复核 |
| `[X]` | 已证伪 | 试过不通，附原因 |

**继承来的结论默认 `[?]`**，除非本会话重新验证过。不要把别人的推断洗成事实。
